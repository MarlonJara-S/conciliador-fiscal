# ADR 0005: Manage dependencies with uv instead of pip-tools

- **Status:** Accepted
- **Date:** 2026-10-14

## Context

P1 managed its environment with `python -m venv`, `pip`, and `pip-tools`: dependencies were declared in `requirements.in` / `requirements-dev.in`, pinned with `pip-compile` into `requirements.txt` / `requirements-dev.txt`, and installed with `pip-sync`.

The approach is correct and reproducible, but:

- Adding one dependency takes four steps (edit `.in`, `pip-compile` twice, `pip-sync`), and the order matters because the dev file is constrained by the production file.
- Dependencies live outside `pyproject.toml`, which already holds the project metadata and tool configuration.
- The Python version is not managed by the tooling.
- In CI, installing dependencies is the slowest step: 8 to 12 seconds out of a 20 to 33 second run (median about 25 seconds over the last 11 successful runs).

uv (by Astral, the authors of ruff) has become the common choice for new Python projects in 2025–2026.

## Decision

Use **uv** for environments and dependencies:

- Runtime dependencies in `[project].dependencies` of `pyproject.toml`; development tools in `[dependency-groups].dev`.
- Exact versions, including transitive ones, in `uv.lock`, generated by uv and committed. It is never edited by hand.
- Python version pinned in `.python-version` (3.13).
- `uv sync` installs the exact environment locally; CI runs `uv sync --frozen`, which fails if `uv.lock` is out of date with `pyproject.toml`.
- Commands run through `uv run` (for example `uv run pytest`), so the environment does not need to be activated.
- `ruff` is pinned to the same version as the pre-commit hook (`0.16.10`), so the editor, pre-commit, and CI always agree.

## Alternatives considered

**Keep pip-tools.** Rejected. It works and the team understands it, but it needs more steps per change, keeps dependencies outside `pyproject.toml`, and is slower in CI. Its concepts (declared vs. locked dependencies, sync) carry over unchanged to uv.

**Poetry.** Rejected. It also provides `pyproject.toml` declarations and a lock file, but it is slower than uv, does not manage Python versions, and uses its own extensions to `pyproject.toml` in older versions.

**Plain `pip install -r requirements.txt` without a lock tool.** Rejected. Transitive dependencies would not be pinned, so environments would not be reproducible.

## Consequences

**Positive**

- One tool and one command (`uv sync`) for local setup, CI, and, later, Docker images (`uv sync --frozen --no-dev`).
- Adding a dependency is one command (`uv add`).
- The same mental model as the frontend package managers that come later (`package.json` + lock file).

**Negative and risks**

- A new tool to learn and keep installed on each machine.
- Platforms that only accept `requirements.txt` need an exported file (`uv export`).

**How we will know it was a good decision**

- CI time, measured on the first runs after the migration, compared with the baseline above (median about 25 seconds, of which 8 to 12 seconds were dependency installation).
- No CI failure caused by environment differences between local and CI.

## Results

First CI run after the migration (pull request, 2026-10-14):

| Step | Before (pip-tools) | After (uv) |
|---|---|---|
| Set up Python / uv | 2–4 s | 1 s |
| Install dependencies | 8–12 s | 1 s |
| Lint, format, types, tests, audit | 3–4 s | 4 s |
| Whole run | 20–33 s (median ~25 s) | 17 s |

Dependency installation dropped from about 10 seconds to 1, and the whole run from a median of about 25 seconds to 17 (about 30% less). This is a single run; later runs on `main` will confirm it. The first CI attempt failed because `astral-sh/setup-uv` publishes no floating `v10` tag; the action is now pinned to the commit SHA of `v10.3.0`.
